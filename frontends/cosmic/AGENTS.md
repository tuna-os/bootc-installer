# AGENTS.md — agent guide for frontends/cosmic (formerly tuna-os/tuna-installer-cosmic)

> **Monorepo note.** This directory is one of five frontends in
> `tuna-os/bootc-installer`. Every path below is relative to THIS directory.
> Workflows referenced as `screenshots.yml` / `publish-flatpak.yml` / `ci.yml`
> are now `.github/workflows/screenshots-cosmic.yml`, `publish-flatpak.yml` (`frontend: cosmic`)
> (plus `ci-niri.yml` for the niri Go backend) at the repository root, running with
> `working-directory: frontends/cosmic`. The shared recipe schema and screen
> contract live in `../../shared/`. Do not add a `.github/` here.

A real **COSMIC** application — `cosmic::Application`, the COSMIC header bar,
the cosmic widget set and the `cosmic-theme` palette — that drives the
[fisherman](https://github.com/tuna-os/fisherman) bootc install backend.

Human docs: [`README.md`](README.md), [`DESIGN.md`](DESIGN.md),
[`docs/gui-walkthrough.md`](docs/gui-walkthrough.md).

## The build gate is the screenshot job

This is the thing to internalise before changing anything: **`screenshots.yml`
is the only CI job that compiles this crate** (the E2E job compiles it too,
for one ignored test). There is no `ci.yml`. The screenshot job also runs
the whole unit suite (`cargo test --release --locked`): the shared catalog
fixture, the account groups, the fisherman resolver and the strings lint.

That is not an accident of history, it is the reason the job exists. Before it,
nothing in CI ran `cargo build` — and the crate *did not build*: the source was
written against the iced 0.13 API while `Cargo.toml` asked for 0.14, so
`cargo build` failed on five errors and the installer could not start at all.
Only `publish-flatpak` ran, and it never reached a cargo build.

Two consequences:

- **The gate is path-filtered** to `src/**`, `Cargo.toml`, `Cargo.lock`, the
  shared contracts that the tests read and the workflow file. A PR that touches only docs or the justfile gets **no build
  signal at all** — a green PR page means "nothing ran", not "it compiles".
- Run the build yourself before pushing anything that touches `src/`:

  ```bash
  # libcosmic needs these headers even when it will run under X11
  sudo apt-get install -y pkg-config cmake clang \
    libwayland-dev libxkbcommon-dev libfontconfig-dev libfreetype-dev \
    libinput-dev libudev-dev libgbm-dev libegl1-mesa-dev libssl-dev

  just check          # cargo build
  just run            # cargo run --release
  just capture        # the screenshot harness, locally
  ```

## Headless rendering is not the GTK story

libcosmic is iced-on-wgpu and needs a **real graphics device**, so Xvfb alone
is not enough the way it is for the GTK/Qt siblings. CI gives wgpu a CPU Vulkan
adapter via Mesa's **lavapipe**. No Wayland compositor is involved —
libcosmic's winit runs on the X11 backend under Xvfb, which is what keeps this
a capture task rather than a "run cosmic-comp in CI" task.

If a screenshot job fails with an adapter or surface error rather than a Rust
error, that is this machinery, not your UI change.

## `cargo-sources.json` must track `Cargo.lock`

flatpak-builder runs `cargo --offline build`, so `flatpak/cargo-sources.json`
has to describe exactly the crates `Cargo.lock` pins. It is generated by
`just cargo-sources`, and **Renovate automerges lockfile bumps**, so the two
drift silently unless something checks:

```bash
just check-cargo-sources            # the check
just check-cargo-sources-selftest   # proves the check rejects a desynced file
```

`cargo-sources.yml` runs both — the selftest is there so the check cannot rot
into something that passes unconditionally. If you bump a dependency,
regenerate the sources file in the same commit.

## Layout

`src/main.rs` (app + update loop), `ui.rs` (screens), `offline.rs` (the
fisherman resolver, the staging and host commands), `image_catalog.rs` (the
catalog reader), `model.rs` (the recipe, `Recipe::apply_leaf`, the account
groups), `validate.rs` (`fisherman validate` and the encryption choices),
`i18n.rs` (`tr`), `readiness.rs`, `branding.rs`, `capture.rs` (the
screenshot harness entry point).

`build.rs` copies three data files from `../../shared/` into `OUT_DIR`:
`branding/copy-defaults.json`, `recipe/encryption-choices.json` and
`account/groups.json`. The code compiles them in from there. This tree has
no copy of them. A build without the monorepo around it sets
`TUNA_SHARED_DIR` to the path of `shared/`. The Flatpak manifest does that:
it has `shared/` as a second source.

## How fisherman is reached

`offline::fisherman_argv` is the one resolver for probe, validation and
install. Do not write a fisherman path, `pkexec` or `sudo` in another
module: `offline::tests::only_the_resolver_names_a_fisherman_path` fails.

- Native: `/usr/local/bin/fisherman`; the install is
  `bash -c 'pkexec /usr/local/bin/fisherman -; exit $?'`, and `sudo -n` in
  place of `pkexec` only on live media (`live.is_live` of the probe).
- Flatpak: the packaged `/app/bin/fisherman` is copied to
  `$XDG_CACHE_HOME/bootc-installer/fisherman` and its SHA256 is checked on
  the host (`stage_on_host`) before the first use. Never `HOME/.cache`.

## The image catalog

`../../shared/catalog/README.md` is the contract.
`image_catalog::tests::the_shared_fixture_resolves_as_expected` reads
`shared/catalog/fixtures/catalog.json` with this parser and compares each
leaf and each recipe with `expected.json`.

- A leaf reaches the recipe only through `Recipe::apply_leaf`: image,
  `targetImgref`, bootloader, `composeFsBackend`, filesystem, Flatpaks,
  `flatpakVarPath`, `imageType`, and the NVIDIA rule.
- `needs_user_creation` is `true` when no node sets it.
- Nothing is selected at the start unless the branding or the catalog names
  a `default_image`. Do not select the first row.
- `flatpaks` is in the recipe only for a list that resolves offline. Do not
  download a list and do not read `fallback_flatpaks`.

## Strings

Every user-facing line is a branding copy key (`branding::text`) or a
message id in `ui::copy` that goes through `i18n::tr`.
`ui::tests::no_widget_takes_a_bare_string` fails on a string literal in a
text, label or title call, and on a `copy` constant that does not go
through `tr`. `i18n.rs` says why this is a shim and not `fl!`.

## The recipe, live media and validation

- The recipe goes to `fisherman -` on stdin (`spawn_wrapper`); nothing
  writes it to a file. It holds the LUKS passphrase.
- Live media is the probe's `live.is_live` (`apply_probe`): then `image`
  is left out and fisherman installs the running system.
  `additionalImageStores` stays empty: fisherman exposes the host's stores.
- The hostname, filesystem and encryption rules are fisherman's: the
  options page sends them to `fisherman validate --json --partial -` after
  a pause (`check_fields`), shows a problem through the copy key
  `validate_<code>` and holds Continue on it.
- The account page writes the recipe's `user` block
  (`model::user_block`: username, fullname, password and the groups; left
  out with no username). The groups are `../../shared/account/groups.json`, which
  `build.rs` compiles in, or the operator's `user.groups` in
  `<etc>/bootc-installer/recipe.json`. The page is required unless the
  catalog says that the image on record makes its own first user; then the
  page is skipped and Confirm says so. A custom image that the catalog does
  not have needs an account.
- Cancel on the progress page asks first. A confirmed cancel signals the
  process group of the wrapper. Exit code 130, or a signal after a
  confirmed cancel, shows the cancelled state of the done page
  (`install_outcome`, copy key `done_cancelled_title`). Its username goes into the same
  partial check; the password does not (the non-empty and typed-twice rules
  are this frontend's). A `user.*` problem holds only the account page.
- Encryption choices are `../../shared/recipe/encryption-choices.json`,
  fisherman's file byte for byte, compiled in (`validate::choices`). Branch on
  `needs_passphrase` / `needs_tpm2`, never on the type's name.

`../../shared/recipe/README.md` is the contract.

Every user-facing string lives in `ui::copy`. The views and `ui::page_text`
both read from it, and the capture harness writes `page_text` to
`docs/screenshots/texts.json` for the shared parity report. Add a string to
`copy` and to `page_text` when you add it to a view, or the parity matrix
stops seeing that screen.

## Disks, TPM and minimum requirements

These come from `fisherman probe --json`, not from this frontend. `src/probe.rs`
runs `/usr/local/bin/fisherman probe --json` without privileges, off the UI
thread (prefixed with `flatpak-spawn --host` in a Flatpak). It runs at startup
and again when the disk page opens. Show the eligible disks in fisherman's
order, with `size_label` exactly as given. Do not add a disk filter or a size
formatter. If the probe fails, the disk page shows the reason. `cargo test
probe` renders the shared fixtures, and `../../shared/probe/README.md` is the
contract. Capture mode reads `shared/probe/fixtures/laptop.json`.

The confirm page also asks fisherman about the selected image (#266):
`check_source` runs `fisherman probe --json --source` off the UI thread,
and `src/source_check.rs` reads its `capabilities` and `bootc_store`
(#267). Only a blocked source holds Install. A reply for an older visit,
or for another source, is dropped.

The confirm page offers the system that this computer runs as a second
install source (#267). `refresh_reuse` reads the plain probe through
`source_check::reuse_source`. It offers nothing on live media, and the
download stays the default. `install_recipe()` is what the install and the
source check get. fisherman checks the pick (`reuse_problem`). The wizard
skips the network page when this computer can copy its own system. The done page says
"installed, restart required" and never "verified": `receipt_lines()` is
`done_verification` and the line for fisherman's `receipt` event (#269).
`cargo test source_check` reads the shared case files. The capture does not run the
check, so the section is not in the screenshots.
The progress page shows fisherman's `source_reuse` events for a copy of
this computer's system (`ui::source_reuse_text`,
`source_check::source_reuse_lines`, #267). The copy does not move the
bar. During the copy the cancel question says `progress_reuse_cancel`
(`source_check::copy_cancel`). `the_shared_source_reuse_progress_cases`
reads `../../shared/progress/source-reuse-cases.json`.

## Sibling contract

It produces the same recipe JSON as the Qt/KDE installer, shared with all four
frontends through the
[installer frontend contract](https://github.com/tuna-os/tunaos/blob/main/docs/INSTALLER-FRONTENDS.md).
A field added here must exist there too. The real disk work belongs in
fisherman — keep it there.

## Branding

Nothing in this tree names a product. `src/branding.rs` (`branding::get()`, cached; `init()` seeds the recipe from it) resolves the product name,
the recipe's `distroID`, the hostname seed and the default image from a `branding.json`
under `/etc/bootc-installer/` (host first), then `os-release`, then a
neutral "Linux"; the contract and the fixtures it is tested against are in
`shared/branding/` at the monorepo root. `BOOTC_INSTALLER_BRANDING` points
tests at a file, `BOOTC_INSTALLER_PRODUCT_NAME` overrides the name for the
screenshot harness.
Flavour text (welcome, confirm, progress and done lines, the Install button)
is branding copy too: every rebrandable line is a key of
`shared/branding/copy-defaults.json`, read through the same resolver, and
`docs/PARITY.md` records which keys this frontend renders. Add a new
user-facing line the product might want to own as a copy key, not a
literal.
